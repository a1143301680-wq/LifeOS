# LifeOS Architecture

Version: V1 draft
Date: 2026-07-10

## 1. Architecture Summary

LifeOS V1 uses:

- PC Web: React + Vite
- Android App: Native Kotlin
- Backend: Python + FastAPI
- Database: PostgreSQL
- Sync: REST writes + SSE change notifications
- Files: Tencent COS reserved for future attachment support

## 2. Deployment Model

The backend runs on the user's lightweight server under the user's own domain.

V1 is designed for two users and low traffic. The architecture should remain simple and maintainable.

## 3. Client Responsibilities

### PC Web

Responsibilities:

- Project/Goal management
- AI Workspace management
- Dashboard
- Todo viewing and editing
- Calendar aggregation view
- Notes
- Settings management

PC Web does not handle reminder execution in V1.

### Android App

Responsibilities:

- Todo execution
- Normal reminders
- Strong reminders
- Lock-screen full-screen reminders
- Quick add
- Offline Todo operations
- Widgets
- Local cache

Recommended Android local stack:

- Room for local relational cache
- DataStore for lightweight settings and selected identity
- WorkManager for background sync and retry jobs

Android is the source of reminder reliability.

## 4. Backend Responsibilities

The FastAPI backend provides:

- REST API for CRUD operations
- SSE endpoint for change notifications
- User identity separation by `user_id`
- Recurring Todo instance generation
- Basic server-side validation
- Database migrations

V1 does not implement complex authentication.

## 5. Identity and Access

V1 identity model:

- The app stores selected identity locally
- Requests also include a per-identity bootstrap token
- Backend resolves the current `user_id` from the bearer token
- Backend filters all data by the resolved `user_id`

Recommended V1 safety layer:

- A per-identity bootstrap token generated by the backend
- Optional shared family-level server secret for initial bootstrap
- HTTPS through the user's domain
- Tokens can be rotated manually from Settings or a server admin script
- Clients must not pass `user_id` in Phase 1A API requests

Future versions may add proper authentication.

## 6. Synchronization Model

All writes happen through REST API.

V1 uses a lightweight `sync_changes` table for reliable pull recovery.

After a successful write:

1. Backend commits the database transaction
2. Backend writes a `sync_changes` row in the same transaction
3. Backend emits an SSE event to active clients for the same `user_id`
4. Clients receive the event
5. Clients re-fetch affected data or call `GET /api/v1/sync/changes?cursor=...`

SSE event payloads should be lightweight. In Phase 1A, SSE only wakes clients to pull durable changes.

Example event:

```json
{
  "type": "sync.available",
  "latest_cursor": 128,
  "server_time": "2026-07-10T20:00:00+08:00"
}
```

V1 does not implement CRDT, live cursor, or collaborative editing.

Sync recovery rules:

- `GET /api/v1/sync/changes?cursor=...` returns ordered changes and `next_cursor`.
- Cursor must be server-generated, monotonic, and stable.
- Clients must not use local device time as the sync cursor.
- Responses include server time for diagnostics.
- Tombstones must be retained long enough for inactive devices to recover deletions.

## 7. Offline Strategy

Android supports limited offline behavior.

Offline allowed:

- View cached Today Todo
- View recent Todo
- Complete Todo
- Add Todo
- Snooze reminder
- Ignore reminder
- Add quick Note

Online required:

- Full Project/Goal editing
- AI Workspace editing
- Calendar full aggregation
- Heavy settings changes

When Android comes back online, it syncs pending local operations to the backend.

V1 should keep offline conflict handling simple:

- Do not implement field-level merge.
- Use `updated_at` as the default last-write-wins rule.
- Preserve explicit Todo completion over ordinary field edits.
- Let soft delete win over ordinary field edits.
- Avoid conflict popups in V1.
- Avoid editing the same object deeply offline in multiple places.

## 8. Reminder Execution

Reminder scheduling is handled by Android.

Backend stores reminder definitions and sends changes through sync.

Android schedules local notifications or alarm-like full-screen reminders based on synced Reminder records.

Strong reminders require Android permissions such as:

- Notification permission
- Full-screen intent capability where applicable
- Exact alarm permission where applicable
- Battery optimization guidance where applicable

The exact implementation should follow the target Android SDK behavior during development.

## 9. Suggested Backend Data Model

Core tables:

- `users`
- `todo_categories`
- `todos`
- `reminders`
- `reminder_events`
- `recurring_todo_templates`
- `projects`
- `project_stages`
- `milestones`
- `project_logs`
- `ai_sessions`
- `notes`
- `external_links`
- `sync_changes`

Common fields:

- `id`
- `user_id`
- `version` for sync-tracked mutable entities
- `created_at`
- `updated_at`
- `deleted_at` for soft delete where useful

`version` starts at 1 and increments on every server-side mutation. Offline clients may send `base_version` to let the backend detect stale edits.

## 10. Project/Goal Data Notes

The internal model can use `project`.

Product UI should use Project/Goal wording.

Project type controls:

- Default stages
- Display labels
- Feature emphasis

It should not create many hard-coded behavior branches in V1.

## 11. AI Workspace Data Notes

AI Session can be stored as a specialized log record plus structured session table.

Recommended approach:

- `project_logs` stores common timeline fields
- `ai_sessions` stores AI-specific fields and links to `project_logs`

This keeps the project timeline unified while preserving AI-specific structure.

## 12. File and Attachment Strategy

V1 can defer attachment upload.

When needed:

- Store files in COS
- Store metadata and URLs in PostgreSQL
- Link attachments to Notes, Projects, AI Sessions, or Todo
