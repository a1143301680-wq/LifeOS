# LifeOS Phase 1A API Specification

Version: V1 draft
Date: 2026-07-10

Scope:

- Identity verification
- Todo Category API
- Todo API
- Today Todo aggregation API
- Sync changes pull API
- SSE wake-up API

Out of scope for Phase 1A:

- Reminder API
- Recurring Todo API
- Reminder events
- Android offline pending operation replay API
- Strong reminder API
- Full login/account system

## 1. API Principles

Base path:

```text
/api/v1
```

Phase 1A is the smallest cross-device Todo loop:

> Two identity-separated users can create, edit, complete, reopen, delete, and sync Todo data between PC Web and Android.

The API should stay explicit and boring:

- Token decides the current user.
- Clients never send `user_id`.
- All writes are idempotent.
- All writes create `sync_changes`.
- SSE only wakes clients up; sync data is pulled through `sync_changes`.

## 2. Authentication

V1 does not implement login.

The backend initializes two users:

- `me`
- `partner`

Each user has a long-lived bootstrap token generated by the server. The database stores only `bootstrap_token_hash`.

Clients manually store the token:

- PC Web: `localStorage` key `lifeos.identityToken`
- Android: DataStore

All authenticated requests use:

```text
Authorization: Bearer <identity_token>
```

Backend behavior:

- Validate token.
- Resolve current `user_id`.
- Filter every query by current `user_id`.
- Reject missing or invalid token with `401 unauthorized`.

The client must not pass `user_id` in request body or query parameters.

Bootstrap token storage:

- Raw tokens are generated from at least 32 bytes of secure random entropy.
- Raw tokens are only shown during initialization or manual rotation.
- The database stores `bootstrap_token_hash` as an Argon2id PHC string.
- Recommended Argon2id parameters: memory cost 64 MiB, time cost 3, parallelism 1.
- Plain SHA-256 token hashes must not be used for stored bootstrap tokens.

PC Web token storage:

- Phase 1A stores the identity token in `localStorage` under `lifeos.identityToken`.
- `lifeos.selectedIdentityAlias` may be stored for UI display only, but must not be trusted for authorization.
- PC Web must provide a local clear/re-enter token path.
- Tokens must not be placed in URLs, logs, analytics, or user-facing error details.
- PC Web should be served through HTTPS.

## 3. Idempotency

All write requests require:

```text
Idempotency-Key: <uuid>
```

Applies to:

- `POST`
- `PATCH`
- `DELETE`
- action endpoints such as `complete` and `reopen`

Backend stores idempotency records in `idempotency_keys`.

Fields:

- `id`
- `user_id`
- `key`
- `method`
- `path`
- `request_hash`
- `response_status`
- `response_body`
- `created_at`
- `expires_at`

Constraints:

- unique `(user_id, key)`

Retention:

- 7 days

Rules:

- Missing key returns `400 idempotency_key_required`.
- Same user + same key + same request returns the original response.
- Same user + same key + different request returns `409 idempotency_key_conflict`.

Request hash:

```text
request_hash = sha256(
  method + "\n" +
  normalized_path + "\n" +
  canonical_query + "\n" +
  canonical_json_body
)
```

Canonicalization rules:

- `method` is uppercase, such as `POST`.
- `normalized_path` is the API path without scheme or host, such as `/api/v1/todos`.
- `canonical_query` sorts query parameters by key and value before encoding; no query is an empty string.
- `canonical_json_body` serializes JSON with sorted keys and no insignificant whitespace; no body is an empty string.
- The hash excludes `Authorization`, `Idempotency-Key`, and volatile headers such as `User-Agent`.
- SHA-256 is used only to compare request fingerprints for idempotency reuse; it is not used for token storage.

## 4. Response Envelope

Single object:

```json
{
  "data": {},
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

List:

```json
{
  "items": [],
  "next_cursor": null,
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

Write response:

```json
{
  "data": {},
  "sync": {
    "cursor": 128
  },
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

Error:

```json
{
  "error": {
    "code": "validation_error",
    "message": "title is required",
    "details": {}
  },
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

## 5. Error Codes

Initial stable error codes:

- `unauthorized`
- `forbidden`
- `not_found`
- `validation_error`
- `idempotency_key_required`
- `idempotency_key_conflict`
- `invalid_state_transition`
- `deleted_resource`
- `rate_limited`
- `internal_error`

## 6. Time Format

Timestamp fields use ISO 8601 with timezone:

```text
2026-07-10T18:30:00+08:00
```

Date-only fields use:

```text
YYYY-MM-DD
```

Examples:

- `planned_date`: date-only
- `due_at`: timestamp
- `completed_at`: timestamp
- `created_at`: timestamp
- `updated_at`: timestamp

Today API uses the current user's timezone, default `Asia/Shanghai`, to calculate day boundaries.

## 9. Todo Category API

## 9.1 List Categories

```text
GET /api/v1/todo-categories
```

Returns active categories only.

Ordering:

1. `sort_order ASC`
2. `created_at ASC`

Response:

```json
{
  "items": [],
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

## 9.2 Create Category

```text
POST /api/v1/todo-categories
Idempotency-Key: <uuid>
```

Request:

```json
{
  "name": "Pet",
  "color": "#22c55e",
  "icon": "paw",
  "sort_order": 10
}
```

Rules:

- `is_inbox` cannot be set by clients.
- If `sort_order` is omitted, the server appends the category to the end.
- Category names should be unique among active categories for the user.

## 9.3 Update Category

```text
PATCH /api/v1/todo-categories/{id}
Idempotency-Key: <uuid>
```

Allowed fields:

- `name`
- `color`
- `icon`
- `sort_order`

Forbidden fields:

- `is_inbox`
- `user_id`
- system timestamps

Inbox rules:

- Inbox can update display fields.
- Inbox cannot be deleted.
- Inbox cannot be converted to a normal category.
- Other categories cannot be converted to Inbox.

## 9.4 Delete Category

```text
DELETE /api/v1/todo-categories/{id}
Idempotency-Key: <uuid>
```

Rules:

- Soft delete only.
- Inbox cannot be deleted.
- Existing Todos keep their `category_id`.
- New create/edit Todo requests cannot select a deleted category.
- Normal category lists hide deleted categories.
- Historical Todo DTOs may show category as deleted.

## 10. Todo API

## 10.1 List Todos

```text
GET /api/v1/todos
```

Query parameters:

- `status`: `pending`, `completed`, `all`; default `pending`
- `category_id`: optional UUID
- `planned_date`: optional `YYYY-MM-DD`
- `due_from`: optional ISO timestamp
- `due_to`: optional ISO timestamp
- `limit`: default 50, max 100
- `cursor`: opaque list cursor

Default behavior:

- Excludes soft-deleted Todos.
- Defaults to `status=pending`.

Default ordering:

1. `planned_date ASC`, null last
2. `due_at ASC`, null last
3. priority `high > medium > low`
4. `updated_at DESC`
5. `id ASC`

Response:

```json
{
  "items": [],
  "next_cursor": null,
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

Opaque cursor format:

- Todo list pagination uses a base64url-encoded JSON cursor.
- The cursor is opaque to clients. Clients store and return it without parsing.
- The cursor includes a version and the final item ordering anchor:

```json
{
  "v": 1,
  "planned_date": "2026-07-10",
  "due_at": "2026-07-10T18:30:00+08:00",
  "priority_rank": 1,
  "updated_at": "2026-07-10T18:31:00+08:00",
  "id": "uuid"
}
```

Cursor rules:

- `priority_rank` uses lower values for earlier sort order, for example `high = 1`, `medium = 2`, `low = 3`.
- Null ordering must be expressed explicitly in backend queries.
- Invalid or undecodable cursors return `400 validation_error`.
- Cursors are tied to the current filter and sort. If query filters change, clients should restart from the first page.
- Phase 1A does not require cursor encryption or signing.

## 10.2 Create Todo

```text
POST /api/v1/todos
Idempotency-Key: <uuid>
```

Request:

```json
{
  "id": "optional-client-generated-uuid",
  "title": "Feed birds",
  "note": null,
  "category_id": "uuid",
  "priority": "medium",
  "planned_date": "2026-07-10",
  "due_at": null
}
```

Rules:

- `id` is optional.
- If `id` is omitted, the server generates a UUID.
- If `id` is provided, it must be a valid UUID.
- Clients cannot send `user_id`.
- `status` is always created as `pending`.
- If `category_id` is omitted, server uses the user's Inbox.
- Deleted categories cannot be selected.

Response includes the created Todo and `sync.cursor`.

## 10.3 Get Todo

```text
GET /api/v1/todos/{id}
```

Rules:

- Only returns Todo owned by current token user.
- Missing Todo or Todo owned by another user returns `404 not_found`.
- Soft-deleted Todo owned by the current user returns `410 deleted_resource`.
- Soft-deleted Todo response uses the standard error envelope with code `deleted_resource`.

## 10.4 Update Todo

```text
PATCH /api/v1/todos/{id}
Idempotency-Key: <uuid>
```

Allowed fields:

- `title`
- `note`
- `category_id`
- `priority`
- `planned_date`
- `due_at`

Forbidden fields:

- `status`
- `completed_at`
- `deleted_at`
- `user_id`
- `version`
- `created_at`
- `updated_at`

Rules:

- Deleted Todo cannot be updated.
- Deleted category cannot be selected.
- Status changes must use action endpoints.

## 10.5 Complete Todo

```text
POST /api/v1/todos/{id}/complete
Idempotency-Key: <uuid>
```

Rules:

- `pending -> completed`
- Set `completed_at` using server time.
- Write `sync_changes: todo.completed`.
- Deleted Todo cannot be completed.
- Repeating the same idempotency key returns the original result.

## 10.6 Reopen Todo

```text
POST /api/v1/todos/{id}/reopen
Idempotency-Key: <uuid>
```

Rules:

- `completed -> pending`
- Clear `completed_at`.
- Write `sync_changes: todo.reopened`.
- Deleted Todo cannot be reopened.
- `canceled` reopen is not supported in Phase 1A.

## 10.7 Delete Todo

```text
DELETE /api/v1/todos/{id}
Idempotency-Key: <uuid>
```

Rules:

- Soft delete only.
- Set `deleted_at`.
- Do not force `status = canceled`.
- Write `sync_changes: todo.deleted`.
- Normal Todo lists do not return deleted Todos.
- Sync changes return tombstone information.

## 11. Today Todo API

## 11.1 Get Today Todo

```text
GET /api/v1/todos/today?date=2026-07-10
```

Rules:

- Uses current user's timezone.
- Returns homepage aggregation, not a naked Todo list.
- Does not paginate.
- Phase 1A has no Reminder section.

Sections:

- `overdue`
- `due`
- `planned`
- `inbox_recent`

Single-assignment priority:

1. `overdue`
2. `due`
3. `planned`
4. `inbox_recent`

Section rules:

- `overdue`: pending Todo with `due_at` before the start of the selected date.
- `due`: pending Todo with `due_at` inside the selected date.
- `planned`: pending Todo with `planned_date = date`.
- `inbox_recent`: pending Inbox Todo with no `planned_date`, no `due_at`, sorted by recent creation, max 5.

Ordering inside each section:

1. priority `high > medium > low`
2. `due_at ASC`, null last
3. `planned_date ASC`
4. `created_at ASC`

Response:

```json
{
  "data": {
    "date": "2026-07-10",
    "timezone": "Asia/Shanghai",
    "sections": {
      "overdue": [],
      "due": [],
      "planned": [],
      "inbox_recent": []
    },
    "summary": {
      "pending_count": 0,
      "completed_count": 0,
      "overdue_count": 0
    }
  },
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

## 12. Sync Changes API

## 12.1 Pull Changes

```text
GET /api/v1/sync/changes?cursor=0&limit=100
```

Query parameters:

- `cursor`: global sync cursor known by the client; default 0 for first sync
- `limit`: default 100, max 500

Rules:

- `sync_changes.cursor` is a global monotonically increasing bigint.
- Clients only receive changes for the current token user.
- Cursor gaps are valid.
- Results are ordered by `cursor ASC`.
- If no current-user items exist, `next_cursor` still returns the current global server cursor.
- Client stores `next_cursor` as the next local sync cursor.
- Client loops while `has_more = true`.

Response:

```json
{
  "items": [
    {
      "cursor": 101,
      "change_type": "todo.updated",
      "entity_type": "todo",
      "entity_id": "uuid",
      "entity_version": 3,
      "snapshot": {}
    }
  ],
  "next_cursor": 128,
  "has_more": false,
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

Tombstone example:

```json
{
  "cursor": 102,
  "change_type": "todo.deleted",
  "entity_type": "todo",
  "entity_id": "uuid",
  "entity_version": 4,
  "deleted": true,
  "deleted_at": "2026-07-10T18:30:00+08:00"
}
```

Change payload rules:

- create/update/complete/reopen include `snapshot`.
- delete includes tombstone fields.
- Snapshot is lightweight but sufficient for local cache updates.
- This is not event sourcing; it is sync recovery data.

## 13. SSE API

## 13.1 Subscribe To Sync Events

```text
GET /api/v1/sync/events
Authorization: Bearer <token>
```

SSE sends wake-up events only.

Event:

```json
{
  "type": "sync.available",
  "latest_cursor": 128,
  "server_time": "2026-07-10T18:30:00+08:00"
}
```

Client behavior:

1. Receive `sync.available`.
2. Call `GET /api/v1/sync/changes?cursor=<local_cursor>`.
3. Apply snapshots or tombstones to local cache.

SSE must not send entity snapshots.

## 15. Closed Implementation Decisions

Resolved before coding:

- `GET /api/v1/todos/{id}` returns `410 deleted_resource` for current-user soft-deleted Todo, and `404 not_found` for missing or cross-user Todo.
- Bootstrap tokens are stored as Argon2id PHC strings, with 64 MiB memory cost, time cost 3, and parallelism 1 as the initial target parameters.
- Idempotency request hashes use SHA-256 over a canonical request fingerprint.
- Todo list cursors use base64url JSON v1 cursors anchored to the final item ordering fields.
- PC Web stores the identity token in `localStorage` under `lifeos.identityToken` for Phase 1A.

Phase 1A implementation may now proceed to backend code skeleton design.
